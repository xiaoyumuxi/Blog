## MySQL
<details>
<summary>**B+ 树、聚簇索引、二级索引**</summary>
<details>
<summary>为什么 InnoDB 用 B+ 树？</summary>
B+ 树扇出高、树矮，可以减少磁盘 IO，而且叶子节点有序连接，适合范围查询；**红黑树也能做范围查询，但树更高、磁盘 IO 更多；Hash 不适合范围查询和排序。**
</details>
<details>
<summary>聚簇索引和二级索引有什么区别？</summary>
聚簇索引叶子节点保存完整行记录，二级索引叶子节点保存索引列和主键值。
</details>
</details>
<details>
<summary>**回表、覆盖索引、最左匹配、索引失效**</summary>
<details>
<summary>什么是回表？</summary>
通过二级索引找到主键后，再根据主键访问聚簇索引获取完整行记录，这个过程叫回表。
</details>
<details>
<summary>什么是覆盖索引？</summary>
查询所需字段全部包含在某个索引中，可以直接从索引返回结果，从而避免回表。
</details>
<details>
<summary>什么是最左匹配？</summary>
联合索引需要从最左侧列开始形成**连续前缀匹配**，因为 B+ 树先按第一列排序，第一列相同时才继续按后续列排序；**它不是看 WHERE 条件书写顺序，不满足最左前缀也不等于一定全表扫描。**
</details>
<details>
<summary>常见索引不能被高效利用的情况？</summary>
联合索引不满足最左前缀、对索引列使用函数、发生隐式类型转换等都会让索引难以直接用于高效定位。
</details>
</details>
<details>
<summary>**ACID、隔离级别**</summary>
<details>
<summary>ACID 是什么？</summary>
Atomicity 原子性、**Consistency 一致性**、Isolation 隔离性、**Durability 持久性**；原子性主要靠 undo log，隔离性靠 MVCC 和锁，持久性靠 redo log，**一致性是事务最终要达到的正确状态，不是某一个单独日志直接“实现”的。**
</details>
<details>
<summary>为什么需要隔离级别？</summary>
多事务并发会产生脏读、不可重复读、幻读等问题，隔离级别用于在数据一致性和并发性能之间做权衡。
</details>
<details>
<summary>四种隔离级别是什么？</summary>
从低到高分别是读未提交 RU、读已提交 RC、可重复读 RR、串行化 Serializable。
</details>
<details>
<summary>什么是脏读、不可重复读和幻读？</summary>
**脏读 = 读到其他事务尚未提交的数据**；**不可重复读 = 同一事务两次读取同一行结果不同**；**幻读 = 两次相同范围查询的结果集出现新增或消失的行。**
</details>
</details>
<details>
<summary>**MVCC、Read View、RC / RR**</summary>
<details>
<summary>什么是 MVCC？</summary>
MVCC 是多版本并发控制，核心依赖**隐藏字段 + undo log 版本链 + Read View**，在保证事务隔离性的同时提高读写并发性能；**redo log、Gap Lock、Next-Key Lock 都不是 MVCC 的核心组成。**
</details>
<details>
<summary>Read View 是干什么的？</summary>
**Read View 本身不保存某一时刻的数据快照**，而是根据事务 ID 判断版本链中的某条记录版本对当前事务是否可见。
</details>
<details>
<summary>RC 和 RR 的核心区别是什么？</summary>
RC 每次快照读都会生成新的 Read View，而 RR 通常在第一次快照读时生成并复用，因此 RR 能实现可重复读。
</details>
<details>
<summary>RR 为什么仍可能出现特殊幻读？</summary>
如果同一事务先快照读、后切换到当前读，或先看不到其他事务的新记录但随后自己 UPDATE 了该记录，就可能看到与原快照不同的数据。
</details>
</details>
<details>
<summary>**快照读、当前读**</summary>
<details>
<summary>什么是快照读？</summary>
快照读基于 MVCC 和 Read View 读取对当前事务可见的数据版本，普通 SELECT 通常属于快照读。
</details>
<details>
<summary>什么是当前读？</summary>
当前读读取最新的已提交版本并对相关记录加锁，例如 SELECT ... FOR UPDATE、UPDATE、DELETE。
</details>
<details>
<summary>为什么普通 SELECT 通常不阻塞 UPDATE？</summary>
普通 SELECT 通过 MVCC 读取可见版本，不需要和 UPDATE 争抢同一条记录的写锁，因此读写多数情况下可以并发。
</details>
<details>
<summary>为什么 UPDATE 可能阻塞另一个 UPDATE？</summary>
UPDATE 会对相关记录申请**排他锁（X Lock）**，如果两个事务修改同一条记录或重叠的加锁范围，就会发生锁冲突并等待；**最常见原因是记录上的排他锁冲突，不是简单归因于 Gap Lock。**
</details>
</details>
<details>
<summary>**Record / Gap / Next-Key Lock**</summary>
<details>
<summary>什么是 Record Lock（记录锁）？</summary>
锁住某条索引记录。
</details>
<details>
<summary>什么是 Gap Lock（间隙锁）？</summary>
锁住相邻索引记录之间的间隙，不锁已有记录本身，主要阻止其他事务向间隙插入新记录。
</details>
<details>
<summary>什么是 Next-Key Lock（临键锁）？</summary>
Record Lock + Gap Lock，通常锁住一条索引记录以及它前面的间隙，例如 `(10,20]`。
</details>
<details>
<summary>RR 为什么还需要 Gap Lock / Next-Key Lock？</summary>
MVCC 主要处理快照读，而当前读需要读取最新数据，因此要通过范围锁阻止其他事务在当前读的扫描范围内插入新记录，避免幻读。
</details>
</details>
<details>
<summary>**redo / undo / binlog、两阶段提交**</summary>
<details>
<summary>redo log 是干什么的？</summary>
属于 InnoDB，主要用于崩溃恢复和保证事务持久性。
</details>
<details>
<summary>undo log 是干什么的？</summary>
属于 InnoDB，**一方面用于事务回滚，另一方面保存历史版本，配合 Read View 实现 MVCC。**
</details>
<details>
<summary>binlog 是干什么的？</summary>
属于 Server 层，主要用于主从复制和基于时间点的数据恢复。
</details>
<details>
<summary>为什么需要两阶段提交？</summary>
为了保证 redo log 和 binlog 的一致性，提交时**先写 redo prepare → 再写 binlog → 最后 redo commit**；崩溃恢复时，**若 redo 处于 prepare，就根据 binlog 是否完整决定提交还是回滚，而不是“用 redo 把 binlog 补回来”。**
</details>
</details>
<details>
<summary>**死锁**</summary>
<details>
<summary>什么是死锁？</summary>
多个事务互相持有对方需要的锁并形成循环等待，就是死锁。
</details>
<details>
<summary>怎么降低死锁概率？</summary>
**统一加锁顺序、缩短事务、建立合适索引并减少加锁范围**；InnoDB 检测到死锁后会回滚其中一个事务，应用层需要支持事务重试；**不是简单把一条 SQL 拆成多条就能避免死锁。**
</details>
</details>
<details>
<summary>**刷盘机制**</summary>
<details>
<summary>什么是刷盘？为什么不能每次 UPDATE 都直接把数据页刷到磁盘？</summary>
刷盘就是把内存中的数据持久化到磁盘。InnoDB 修改数据时会先修改 Buffer Pool 中的数据页，并记录 redo log；**事务提交时重点保证 redo log 持久化，并不等于立刻把数据页刷到磁盘。** 被修改但尚未落盘的数据页叫脏页，之后由后台异步刷盘。这样通过 WAL 机制用 redo log 的顺序写减少频繁的数据页随机写，在降低磁盘 IO 的同时保证崩溃后可恢复。
</details>
</details>
<details>
<summary>**主从同步**</summary>
<details>
<summary>MySQL 主从同步是怎么实现的？</summary>
MySQL 主从复制主要基于 Server 层的 binlog。主库把数据变更记录到 binlog，从库的 I/O 线程拉取 binlog 并写入本地 relay log，再由复制应用线程读取 relay log 并应用这些变更，使从库数据逐步与主库保持一致。**核心链路是 binlog → relay log → 应用变更；从库并不一定把它当成普通 SQL 重新执行，Row-Based binlog 记录的是行变更事件。**
</details>
</details>
<details>
<summary>**EXPLAIN用法**</summary>
<details>
<summary>EXPLAIN 是干什么的？主要看哪些字段？</summary>
EXPLAIN 用来查看 SQL 的执行计划，常用于慢 SQL 排查和索引优化。重点看 `type`、`key`、`rows` 和 `Extra`：`type` 表示访问方式，`key` 表示实际使用的索引，**`rows`**** 表示优化器预计扫描的行数，不是实际扫描行数**，`Extra` 可以看到 `Using index`、`Using filesort`、`Using temporary` 等额外信息。
</details>
</details>

## Redis
<details>
<summary>**Redis 基础数据类型与使用场景**</summary>
<details>
<summary>Redis 常见的数据类型有哪些？分别适合什么场景？</summary>
Redis 最常见的数据类型有 String、Hash、List、Set 和 ZSet。String 常用于缓存普通值、计数器等；Hash 适合存对象的多个字段；List 是有序列表，可以用于简单队列；Set 适合去重和集合运算；ZSet 在 Set 的基础上增加 score，适合排行榜等有序场景。**List 可以实现简单队列，但正式消息队列场景更推荐 Streams。**
</details>
</details>
<details>
<summary>**Redis为什么快、线程模型**</summary>
<details>
<summary>Redis 为什么这么快？</summary>
Redis 快主要有四个原因：基于内存读写；针对不同场景设计了高效数据结构；核心命令执行主要采用单线程模型，减少线程切换和锁竞争；使用 IO 多路复用，一个线程可以监听大量网络连接。**Redis 不是整个进程完全只有一个线程，核心命令执行路径才是这里讨论的重点。**
</details>
<details>
<summary>Redis 为什么核心命令执行主要采用单线程？单线程为什么还能支撑高并发？</summary>
Redis 的操作大多是内存访问，CPU 通常不是主要瓶颈；单线程可以避免多线程的锁竞争和上下文切换，同时配合 IO 多路复用，一个线程就能监听并处理大量连接，因此仍然可以支撑较高并发。**这里的 IO 主要指网络 IO，不要理解成磁盘 IO 是 Redis 的核心瓶颈。**
</details>
</details>
<details>
<summary>**RDB / AOF 持久化**</summary>
<details>
<summary>RDB 和 AOF 分别是什么？有什么区别？</summary>
RDB 是把某个时间点的内存数据生成快照并持久化到磁盘；AOF 主要记录会修改数据的写命令。RDB 文件通常更紧凑、恢复更快，但两次快照之间宕机可能丢失一段数据；AOF 的数据丢失窗口通常更小，但文件更大，恢复一般更慢。**AOF 不是记录所有 Redis 操作，而是主要记录写操作。**
</details>
</details>
<details>
<summary>**过期删除**</summary>
<details>
<summary>Redis 中已经过期的 Key 是怎么删除的？</summary>
Redis 的过期删除主要采用惰性删除和定期删除。惰性删除是在访问 Key 时发现已经过期再删除；定期删除是周期性抽样检查部分设置了过期时间的 Key 并删除其中已过期的。这样可以避免每个 Key 到期时都立即处理带来的额外 CPU 和调度开销。**不要把“定期删除”简单说成一定由一个独立后台线程不断扫描全部 Key。**
</details>
</details>
<details>
<summary>**内存淘汰**</summary>
<details>
<summary>Redis 内存满了怎么办？常见的内存淘汰策略有哪些？</summary>
Redis 可以通过 maxmemory 设置最大内存，达到限制后根据 maxmemory-policy 处理。常见策略包括：noeviction，不淘汰数据，新的内存增长型写操作报错；allkeys-lru / allkeys-lfu / allkeys-random，从所有 Key 中淘汰；volatile-lru / volatile-lfu / volatile-random / volatile-ttl，只从设置了 TTL 的 Key 中淘汰。**noeviction 下读取仍然可以进行，并不是“什么操作都不行”；经典八股口径通常是 8 种策略。**
</details>
</details>
<details>
<summary>**缓存穿透、击穿、雪崩**</summary>
<details>
<summary>什么是缓存穿透、缓存击穿和缓存雪崩？分别怎么解决？</summary>
- 缓存穿透是查询数据库里本来就不存在的数据，缓存和数据库都查不到，常用缓存空值或布隆过滤器解决
- 缓存击穿是某个热点 Key 突然失效，大量并发请求同时打到数据库，可用互斥锁或逻辑过期解决
- 缓存雪崩是大量 Key 同时失效，或者 Redis 整体不可用，导致大量请求一起落到数据库，可通过 TTL 加随机值，并配合限流、降级和 Redis 高可用处理。
**逻辑过期更常用于解决热点 Key 的缓存击穿；记忆：穿透=数据不存在，击穿=一个热点 Key 没了，雪崩=一大片 Key 没了。**
</details>
</details>
<details>
<summary>**缓存一致性**</summary>
<details>
<summary>Redis 和 MySQL 双写时，怎么保证缓存一致性？为什么通常先更新数据库，再删除缓存？</summary>
通常采用 Cache Aside 模式：先更新数据库，再删除缓存。因为如果先删缓存，在数据库还没更新时，另一个线程可能缓存未命中并从数据库读到旧值，再把旧值写回 Redis，最后造成数据库是新值、缓存却是旧值。**先更新数据库再删缓存只能降低不一致概率，并不能保证绝对强一致；如果数据库更新成功但删除缓存失败，仍然可能不一致。**
</details>
</details>
<details>
<summary>**分布式锁**</summary>
<details>
<summary>Redis 怎么实现分布式锁？为什么要用 SET key value NX EX？释放锁时为什么不能直接 DEL？</summary>
通常使用 `SET key value NX EX`：`NX` 保证只有 Key 不存在时才能加锁成功，实现互斥；`EX` 设置过期时间，避免持锁服务宕机后锁永久不释放；`value` 使用唯一标识。释放锁时要先校验 value 再删除，并保证“校验 + 删除”原子执行，通常用 Lua 脚本。**不能直接 DEL：自己的锁可能已经过期并被其他线程重新获取，此时直接删除会误删别人的锁。记忆：NX 抢锁 → EX 防死锁 → 唯一 value 防误删。**
</details>
</details>
<details>
<summary>**主从复制**</summary>
<details>
<summary>Redis 主从复制是怎么实现的？全量复制和增量复制有什么区别？</summary>
主从复制用于把主节点的数据同步到从节点，为数据副本和高可用提供基础。全量复制时，主节点生成 RDB 快照发送给从节点，从节点加载后再继续接收后续写命令；断线重连时，从节点通过 replication ID 和 offset 尝试部分重同步，如果缺失的数据还在主节点的 replication backlog 中，就只补发缺失的复制命令流，否则重新做全量同步。**增量复制不是靠 AOF 文件；RDB 主要用于全量复制，增量复制依赖 replication backlog + replication offset。**
</details>
</details>
<details>
<summary>**Sentinel 哨兵**</summary>
<details>
<summary>Redis Sentinel 是干什么的？主节点宕机后怎么故障转移？</summary>
Sentinel 用于主从架构的高可用，会持续监控主从节点。多个 Sentinel 判断主节点下线后，会确认客观下线，并选出一个 Sentinel 执行故障转移：从现有从节点中选择一个合适节点升级为新主，再让其他从节点改为复制新主；旧主恢复后通常作为从节点加入新的主从结构。**不是“从节点之间投票选主”；Sentinel 能降低误切换和脑裂风险，但不能绝对保证网络分区下永不出现脑裂。**
</details>
</details>
<details>
<summary>**Redis Cluster、Hash Slot**</summary>
<details>
<summary>Redis Cluster 怎么做数据分片？为什么不用对节点数量直接取模？</summary>
Redis Cluster 把 Key 空间划分成 16384 个 Hash Slot。Key 通过 `CRC16(key) % 16384` 计算所属槽，再由不同主节点负责不同的槽，因此映射关系是 Key → Slot → 节点。扩缩容时主要重新分配部分槽，并迁移这些槽对应的数据，不需要因为节点数量变化让大量 Key 全部重新映射。**16384 个槽是逻辑 Hash Slot，不是固定的内存块；扩容时迁移的是重新分配的槽及其对应 Key。**
</details>
</details>
<details>
<summary>**BigKey、HotKey**</summary>
<details>
<summary>什么是 BigKey 和 HotKey？分别有什么问题，怎么处理？</summary>
BigKey 是单个 Key 对应的数据量过大，可能造成网络传输耗时、命令执行时间变长、阻塞主线程等问题，常见做法是按业务拆分并避免一次读写过多数据。HotKey 是少数 Key 的访问频率特别高，会造成请求集中到某个节点，形成 CPU、网络或节点负载热点，常见做法是本地缓存、多副本或 Key 拆分、限流等。**HotKey 的核心是访问过于集中，不等同于“缓存被打穿”；预热也不是解决 HotKey 的核心手段。**
</details>
</details>
<details>
<summary>**AOF 重写**</summary>
<details>
<summary>AOF 重写是什么？为什么 AOF 文件会越来越大？重写会不会阻塞主线程？</summary>
AOF 会持续记录写命令，随着运行时间增加，同一个 Key 可能积累大量历史操作，因此文件会不断膨胀。AOF 重写不是直接压缩旧 AOF，而是根据当前内存中的最终数据状态重新生成一份更精简的 AOF，只保留恢复当前状态所需要的命令。重写主体通常由后台子进程完成，不会长时间阻塞主线程，但创建子进程的 fork 阶段可能发生短暂阻塞。**不是简单地“同一个 Key 只保留最后一个操作”；本质是按当前数据状态重新生成 AOF。**
</details>
</details>

## JUC
<details>
<summary>**线程池**</summary>
<details>
<summary>ThreadPoolExecutor 的核心参数有哪些？任务提交后按什么顺序处理？</summary>
ThreadPoolExecutor 常说的 7 个核心参数是：`corePoolSize` 核心线程数、`maximumPoolSize` 最大线程数、`keepAliveTime` 空闲存活时间、`unit` 时间单位、`workQueue` 阻塞队列、`threadFactory` 线程工厂、`handler` 拒绝策略。任务提交后：当前线程数小于核心线程数时创建核心线程；否则尝试进入阻塞队列；队列满且线程数还小于最大线程数时创建非核心线程；**只有队列已满且线程数也达到 maximumPoolSize 时，才会执行拒绝策略。**
</details>
<details>
<summary>线程池常见的四种拒绝策略是什么？</summary>
`AbortPolicy`：直接抛异常；`CallerRunsPolicy`：由提交任务的线程自己执行；`DiscardPolicy`：直接丢弃当前任务，不抛异常；`DiscardOldestPolicy`：丢弃队列中最老的任务，再尝试提交当前任务。**记忆：报错 / 调用者自己跑 / 丢新的 / 丢最老的。**
</details>
</details>
<details>
<summary>**synchronized**</summary>
<details>
<summary>synchronized 是怎么保证线程安全的？可以锁哪些东西？</summary>
synchronized 通过互斥保证同一时刻只有一个线程持有同一把 monitor 锁进入临界区，其他竞争同一把锁的线程需要等待，从而避免共享数据被并发修改。修饰实例方法时锁的是当前 `this` 对象；修饰静态方法时锁的是当前类的 `Class` 对象；同步代码块锁的是括号中指定的对象。**不是“对象一上锁后其他线程就不能访问这个对象”，而是只有竞争同一个 monitor 的线程才会阻塞。**
</details>
</details>
<details>
<summary>**volatile、指令重排序、内存屏障**</summary>
<details>
<summary>volatile 有什么作用？能不能保证线程安全？</summary>
volatile 主要保证两个语义：可见性和有序性。一个线程写入 volatile 变量后，其他线程后续读取时能够看到最新值；同时 volatile 会限制特定的指令重排序。**volatile 不提供互斥，也不能保证复合操作的原子性，因此不能单独保证线程安全；例如 ****`i++`**** 包含读取、计算、写回多个步骤，仍可能发生丢失更新。**
</details>
<details>
<summary>什么是指令重排序？volatile 为什么能限制重排序？</summary>
编译器和 CPU 为了提高执行效率，可能在不改变单线程结果的前提下调整部分指令顺序，但多线程环境下可能产生可见性或发布时序问题。volatile 通过内存屏障限制相关读写跨越屏障重排：可以理解为给指令重排序划定边界。经典例子是双重检查单例，对象创建大致包含“分配内存 → 初始化对象 → 引用赋值”，如果引用赋值被提前，其他线程可能看到非空引用却拿到尚未完成初始化的对象。**volatile 不是禁止所有重排序，而是禁止会破坏其内存语义的特定重排序。**
</details>
</details>
<details>
<summary>**CAS、ReentrantLock、AQS**</summary>
<details>
<summary>CAS 是什么？有什么问题？</summary>
CAS 是 Compare And Swap，也就是比较并交换：比较当前值与预期值，相等时原子地更新为新值，不相等则失败，因此可以基于乐观锁思想实现无锁并发。常见问题有 ABA 和长时间自旋带来的 CPU 开销。ABA 可通过版本号解决，例如 `AtomicStampedReference`。**标准名称是 Compare And Swap，不是 Compare And Set；CAS 自旋开销的基础回答到“长时间自旋耗 CPU”即可，不要说通常靠 sleep 解决。**
</details>
<details>
<summary>synchronized 和 ReentrantLock 有什么核心区别？</summary>
synchronized 会在退出同步区域时自动释放锁；ReentrantLock 需要手动 `unlock()`，通常放在 finally 中。ReentrantLock 还支持可中断获取锁、可配置公平/非公平锁，以及多个 Condition 实现更精细的等待与唤醒。**ReentrantLock 的核心实现应说“基于 AQS”，不是直接概括成“通过 park 实现锁”；park/unpark 是阻塞与唤醒线程时涉及的底层机制。**
</details>
<details>
<summary>什么是 AQS？state 是干什么的？</summary>
AQS 是 JUC 中构建锁和同步器的基础框架，核心维护一个 `state` 同步状态和一个等待队列。线程尝试获取资源时会 CAS 修改 state，失败后进入等待队列并阻塞；资源释放后修改 state，并唤醒等待线程继续竞争。`state` 的具体含义由同步器决定：ReentrantLock 中可表示锁状态和重入次数，Semaphore 中表示剩余许可证数量，CountDownLatch 中表示剩余计数。**公平与非公平的核心区别不是“唤醒几个线程”：公平锁先看队列、按等待顺序竞争；非公平锁允许新线程先尝试抢锁。**
</details>
</details>
<details>
<summary>**ThreadLocal**</summary>
<details>
<summary>ThreadLocal 是干什么的？为什么会有内存泄漏问题？</summary>
ThreadLocal 用于给每个线程保存一份独立的数据，实现线程隔离。每个 `Thread` 内部维护自己的 `ThreadLocalMap`，其中 key 是 ThreadLocal 的弱引用，value 是强引用。如果 ThreadLocal 被回收，key 可能变成 null，但只要线程仍存活，value 仍可能被 ThreadLocalMap 引用而长期残留。线程池中的线程会长期复用，因此使用后通常应在 finally 中调用 `remove()`。**不是“ThreadLocal 自己里面有一个 Map”，也不是“每个线程都有一份 ThreadLocal”；准确说法是每个线程有自己的 ThreadLocalMap，同一个 ThreadLocal 在不同线程中对应不同 value。ThreadLocal 的核心是避免共享，不是在线程之间做同步。**
</details>
</details>
## Java集合
<details>
<summary>**ConcurrentHashMap、HashMap**</summary>
<details>
<summary>ConcurrentHashMap 为什么线程安全？JDK 8 主要用了什么机制？</summary>
JDK 8 的 ConcurrentHashMap 主要通过 CAS 和 synchronized 保证并发安全：目标桶为空时可通过 CAS 插入；桶不为空时，只对当前桶的头节点加 synchronized，再修改该桶中的链表或红黑树。因此不是给整个 Map 加一把大锁，不同桶之间可以并发修改；普通 get 通常不需要加锁。**并发扩容、协助搬迁确实存在，但那是扩容追问，不是回答“为什么线程安全”的主线。记忆：空桶 CAS，非空桶 synchronized，锁桶不锁表。**
</details>
<details>
<summary>HashMap 为什么线程不安全？JDK 8 底层结构是什么？</summary>
JDK 8 HashMap 底层是数组 + 链表 + 红黑树。HashMap 本身没有并发控制，多线程同时 put 时可能同时修改同一个桶，导致覆盖更新、丢失更新；并发扩容时线程之间也可能互相干扰，造成数据迁移异常。**不要只说“数据错位”，应明确说覆盖更新、丢失更新或并发扩容导致结构/迁移异常。**
</details>
<details>
<summary>HashMap 的 put 流程是怎样的？什么时候树化？</summary>
put 时先根据 key 计算 hash 并定位桶；桶为空直接插入；桶不为空时先判断是否存在相同 key，相同则覆盖 value，否则插入链表或红黑树。当链表长度达到树化阈值 8，并且数组容量至少为 64 时，链表会树化；容量不足 64 时通常优先扩容。**是根据 key 计算 hash，不是根据 value；桶不为空时也不是一律直接挂到链表尾部，相同 key 要先覆盖。**
</details>
<details>
<summary>HashMap 为什么容量通常是 2 的幂？</summary>
容量为 2 的幂时，可以用 `hash & (n - 1)` 高效定位桶。扩容通常容量翻倍，扩容后一个元素的新位置只可能保持原位置，或者变成“原位置 + oldCap”，因此位置计算和迁移都更简单。**不是“只移动一半节点”；准确说法是每个节点扩容后只有两个可能位置：原位置或原位置 + oldCap。**
</details>
</details>
<details>
<summary>**ArrayList、LinkedList**</summary>
<details>
<summary>ArrayList 和 LinkedList 有什么区别？</summary>
ArrayList 底层是动态数组，随机访问通常为 O(1)，尾部追加通常也较高效，但中间插入删除需要移动元素。LinkedList 底层是双向链表，随机访问需要遍历；如果已经定位到目标节点，插入删除本身可以 O(1)，但通过下标找到节点仍需要 O(n)。LinkedList 每个节点还需要保存前后引用，额外内存开销更大，因此实际开发中通常更多使用 ArrayList。**不能简单说“LinkedList 插入删除一定更快”；只有已经定位到节点时，插删操作本身才有优势。**
</details>
</details>
## Java基础
<details>
<summary>**==、equals、hashCode**</summary>
<details>
<summary>== 和 equals() 有什么区别？为什么重写 equals() 通常也要重写 hashCode()？</summary>
`==` 对基本类型比较值，对引用类型比较是否指向同一个对象。`Object.equals()` 默认也是引用比较，具体类可以重写 equals 按内容判断。哈希容器会先依据 hashCode 定位桶，再通过 equals 判断逻辑相等，因此如果两个对象 equals 为 true，它们的 hashCode 必须相同；反过来 hashCode 相同并不代表 equals 一定为 true。**equals() 本身并不是“先比较 hashCode 再比较内容”；那是 HashMap / HashSet 等哈希容器查找元素时常见的流程。**
</details>
</details>
<details>
<summary>**String、StringBuilder、StringBuffer**</summary>
<details>
<summary>String 为什么不可变？StringBuilder 和 StringBuffer 有什么区别？</summary>
String 本身是 `final` 类，内部字符内容不会暴露可修改接口，所有看似修改 String 的操作实际上都会产生新的 String 对象。不可变的好处包括更容易保证线程安全、字符串常量池可以安全复用、作为 HashMap Key 时内容和 hash 更稳定。StringBuilder 可变、线程不安全但性能通常更高，适合单线程字符串拼接；StringBuffer 可变且提供同步，线程安全但开销更大。**String 不可变不只是因为类不能被继承，更核心的是对象内部状态不能被外部修改；多线程场景也不是看到并发就一定要用 StringBuffer。**
</details>
</details>
<details>
<summary>**反射**</summary>
<details>
<summary>Java 的反射是什么？有什么优缺点？</summary>
反射是 Java 在运行时动态获取类的信息，并操作构造器、字段和方法的一种机制，也可以通过反射创建对象和调用方法。优点是灵活、动态，便于框架做通用化处理；缺点是相比直接调用存在额外性能开销，类型安全和代码可读性也相对更差。**反射不是“运行时动态创建一个类”，核心是运行时动态获取并操作类的信息；也不要绝对表述成“会慢很多很多”。**
</details>
</details>
<details>
<summary>**异常体系**</summary>
<details>
<summary>Error 和 Exception 有什么区别？Checked Exception 和 RuntimeException 有什么区别？</summary>
Error 一般表示 JVM 或系统层面的严重问题，例如 OutOfMemoryError、StackOverflowError，通常不适合程序主动恢复处理。Exception 表示程序运行过程中可以处理的异常。Checked Exception 编译器要求必须捕获或声明抛出，否则编译不通过；RuntimeException 属于非受检异常，编译器不强制处理，例如 NullPointerException、IndexOutOfBoundsException。**Error 不是“无法编译”，它同样可以在运行时发生；异常被 catch 后是否能正常继续执行，要看具体处理逻辑。**
</details>
</details>
## JVM
<details>
<summary>**JVM 运行时内存区域**</summary>
<details>
<summary>JVM 运行时内存区域有哪些？哪些线程私有，哪些线程共享？</summary>
线程私有区域包括程序计数器、虚拟机栈和本地方法栈；线程共享区域包括堆和方法区。虚拟机栈主要服务 Java 方法，本地方法栈主要服务 Native / JNI 方法；HotSpot 在 JDK 8 之后通常使用元空间 Metaspace 实现方法区。**本地方法栈也是线程私有的，不是共享区域。记忆：计数器 + 两个栈私有；堆 + 方法区共享。**
</details>
</details>
<details>
<summary>**对象分配、新生代、老年代**</summary>
<details>
<summary>对象一般分配在哪里？什么时候进入老年代？</summary>
对象主要分配在堆上，大多数新对象通常先进入新生代 Eden 区；发生 Young / Minor GC 后仍然存活的对象会进入 Survivor，并增加对象年龄。对象经过多次 GC 仍然存活并达到晋升条件后，会进入老年代；传统分代收集器下，某些大对象也可能直接进入老年代。**对象不是固定“经历 16 次 GC 就晋升”；经典 HotSpot 的年龄阈值上限常见为 15，而且实际晋升年龄还可能动态调整。**
</details>
</details>
<details>
<summary>**可达性分析、GC Roots**</summary>
<details>
<summary>JVM 怎么判断对象是不是垃圾？常见 GC Roots 有哪些？</summary>
JVM 主要通过可达性分析判断对象是否可以回收：从一组 GC Roots 作为起点沿引用关系向下搜索，如果一个对象无法从任何 GC Root 到达，就属于不可达对象，后续才可能被回收。常见 GC Roots 包括虚拟机栈中的局部变量引用、类的静态变量、常量引用以及 JNI / Native 持有的引用。**GC Roots 不是“不可变对象”，而是可达性分析的根节点。记忆：栈、静态、常量、JNI。**
</details>
</details>
<details>
<summary>**Minor / Major / Full GC**</summary>
<details>
<summary>Minor GC、Major GC、Full GC 有什么区别？</summary>
Minor GC / Young GC 主要回收新生代，包括 Eden 和 Survivor；Major GC 在传统八股语境下通常指老年代回收；Full GC 的回收范围更大，通常会涉及整个 Java 堆，并可能涉及方法区 / 元空间相关处理，因此停顿和性能开销通常更大。Full GC 可能由老年代空间不足、元空间压力等多种原因触发。**Minor GC 不只是清理 Eden；Full GC 也不是“Minor GC 触发得多了就一定会发生”。**
</details>
</details>
<details>
<summary>**垃圾回收算法与分代**</summary>
<details>
<summary>JVM 常见的垃圾回收算法有哪些？各有什么优缺点？</summary>
标记-清除：先标记垃圾再清除，实现简单，但容易产生内存碎片。复制算法：把存活对象复制到另一块区域，再整体清空原区域，回收后空间连续，但需要额外预留空间，存活对象很多时复制成本较高。标记-整理：先标记存活对象，再把存活对象向一端移动并清理边界外空间，可以避免碎片，但对象移动成本较高。**复制算法不是“复制过去后固定再复制回来”，而是两块区域可以在后续回收中交换角色。**
</details>
<details>
<summary>为什么新生代通常适合复制算法，而老年代更适合标记清除或标记整理？</summary>
新生代对象大多生命周期短，每次 GC 后存活对象少，因此只需复制少量存活对象，成本较低且不会产生碎片。老年代对象通常存活率更高，如果使用复制算法，就需要搬运大量存活对象并预留较大额外空间，因此更适合标记清除或标记整理。**核心原因不是“老年代对象更大”，而是老年代对象通常存活率更高。**
</details>
</details>
<details>
<summary>**类加载与双亲委派**</summary>
<details>
<summary>类加载过程有哪些阶段？双亲委派模型是什么？</summary>
类加载核心过程通常记为：**加载 → 验证 → 准备 → 解析 → 初始化**。加载阶段读取 class 字节码并生成对应 Class 对象；验证检查字节码是否合法；准备阶段为类变量分配内存并设置默认值；解析把符号引用转换为直接引用；初始化阶段执行静态变量赋值和静态代码块。双亲委派指类加载器收到请求后**先委托父加载器处理，只有父加载器无法完成时子加载器才尝试加载**，可减少重复加载并保护核心类。**双亲委派不是“类对象直接被某个加载器加载进 JVM”这么简单。**
</details>
</details>
<details>
<summary>**Java 值传递**</summary>
<details>
<summary>Java 到底是值传递还是引用传递？</summary>
Java 只有值传递。基本类型传递的是值的副本；引用类型传递的是“引用值”的副本。两个引用副本仍可以指向同一个对象，因此方法内部修改对象状态，外部可能看到变化；但如果只是在方法内部让参数引用指向一个新对象，不会改变调用方原来的引用。**不要说 Java 有“引用传递”；引用类型传递的仍然是引用值的副本。**
</details>
</details>

## SSM
<details>
<summary>**IOC / DI**</summary>
<details>
<summary>什么是 IOC？什么是 DI？</summary>
IOC 是控制反转，把对象的创建、管理以及依赖关系交给 Spring 容器，而不是业务代码自己 new 和维护。DI 是依赖注入，是实现 IOC 的主要方式，Spring 在创建 Bean 时把它需要的依赖注入进去。**IOC 不等于“一个存 Bean 的容器”；容器是实现载体，核心是对象控制权交给 Spring。**
</details>
</details>
<details>
<summary>**AOP**</summary>
<details>
<summary>什么是 AOP？Spring AOP 一般用来做什么？</summary>
AOP 是面向切面编程，把日志、权限、事务、监控等横切逻辑从业务代码中抽离，再通过代理统一增强目标方法，从而减少重复代码和业务耦合。Spring AOP 常通过 JDK 动态代理或 CGLIB 实现。**AOP 不只是“在方法前面加代码”，增强逻辑可以发生在方法执行前、后或异常等多个位置。**
</details>
</details>
<details>
<summary>**Bean 生命周期**</summary>
<details>
<summary>Spring Bean 的生命周期大致有哪些阶段？</summary>
核心记忆：**实例化 → 依赖注入 → 初始化 → 使用 → 销毁**。Spring 先创建 Bean，再注入依赖并执行初始化相关逻辑，之后 Bean 进入可用状态；容器关闭时执行销毁逻辑。
</details>
</details>
<details>
<summary>**Spring 事务**</summary>
<details>
<summary>Spring 事务是怎么实现的？@Transactional 在什么情况下会失效？</summary>
Spring 声明式事务主要通过 AOP 代理实现：目标方法执行前开启事务，正常结束后提交，出现满足回滚条件的异常时回滚。常见失效场景包括**同类内部调用绕过代理、对象不是 Spring 管理的 Bean、异常被 catch 后没有继续抛出**。Spring 默认主要对 RuntimeException 和 Error 回滚。**事务失效优先检查：有没有经过代理、对象是否由 Spring 管理、异常是否真正抛给了事务拦截器。**
</details>
</details>
<details>
<summary>**Spring MVC**</summary>
<details>
<summary>Spring MVC 一次请求从浏览器到 Controller 返回结果，大致经过什么流程？</summary>
请求先进入 **DispatcherServlet**，由它根据请求信息找到并调用对应的 **Controller** 方法；Controller 处理完成后返回数据或视图，Spring MVC 再把结果转换成 HTTP 响应返回客户端。前后端分离项目中，返回对象通常会被序列化成 JSON。

<details>
<summary>**MyBatis 参数占位**</summary>
<details>
<summary>MyBatis 中 `#{}` 和 `${}` 有什么区别？</summary>
`#{}` 会使用预编译参数占位，底层类似 PreparedStatement 的 `?`，参数单独绑定，能够避免大部分 SQL 注入；`${}` 是直接进行字符串拼接，存在 SQL 注入风险。一般查询条件优先使用 `#{}`；表名、字段名、排序字段等无法作为普通参数占位的位置才可能使用 `${}`，并且需要严格校验输入。**记忆：****`#{}`**** 传值，****`${}`**** 拼 SQL。**
</details>
</details>

## 计算机网络
<details>
<summary>**TCP 三次握手**</summary>
<details>
<summary>TCP 为什么需要三次握手，而不是两次？</summary>
TCP 三次握手主要是为了确认通信双方的发送和接收能力都正常。第一次客户端发送 SYN，服务端确认客户端能发送、自己能接收；第二次服务端返回 SYN + ACK，客户端确认服务端能发送和接收；第三次客户端返回 ACK，服务端最终确认客户端也能正常接收。**不要只回答“为了确认 ACK 是否到达”或“丢了就重传”；更核心的是双方都确认彼此的收发能力。**
</details>
<details>
<summary>为什么三次握手可以避免旧的重复 SYN 导致误建连接？</summary>
如果网络中滞留的历史 SYN 很晚才到达服务端，服务端会先回复 SYN + ACK；只有客户端继续完成第三次 ACK，连接才会真正建立。客户端如果当前并没有发起该连接，就不会正常完成这次确认，因此服务端不会把一个过期请求误认为新的有效连接。**第三次握手还能让服务端确认：客户端现在确实仍然想建立这条连接，而不是只收到了历史遗留 SYN。**
</details>
</details>
<details>
<summary>**TCP 四次挥手与 TIME_WAIT**</summary>
<details>
<summary>TCP 为什么通常需要四次挥手？</summary>
TCP 是全双工通信，两个方向需要分别关闭。主动关闭方先发送 FIN，对方回复 ACK；但对方此时可能还有剩余数据要发送，因此不能立刻同时发送 FIN。等剩余数据发送完成后，对方再发送 FIN，主动关闭方最后回复 ACK，所以通常是 FIN → ACK → FIN → ACK。**核心不是“防止只释放一部分资源”，而是 TCP 两个方向要分别关闭；第一次 FIN 后还可能处于半关闭状态。**
</details>
<details>
<summary>为什么主动关闭的一方要进入 TIME_WAIT？</summary>
主动关闭方发送最后一个 ACK 后会进入 TIME_WAIT。第一，如果最后 ACK 丢失，对方会重发 FIN，此时还能再次回复 ACK，保证连接可靠关闭；第二，让旧连接中滞留的历史报文在网络中自然失效，避免影响后续复用相同四元组建立的新连接。传统表述通常等待 2MSL。**TIME_WAIT 不是为了继续等待对方把剩余数据发完；进入 TIME_WAIT 时，对方已经发送 FIN。记忆：保证最后 ACK + 清理历史报文。**
</details>
</details>
<details>
<summary>**TCP 与 UDP**</summary>
<details>
<summary>TCP 和 UDP 有什么区别？</summary>
TCP 面向连接、提供可靠传输、面向字节流，并提供**确认、重传、流量控制和拥塞控制**等机制，因此开销相对更大。UDP 无连接、不保证可靠传输、面向报文，协议开销更小、延迟通常更低。**“TCP 用四元组标识连接”可以说，但不是 TCP 与 UDP 最核心的区别。**
</details>
</details>
<details>
<summary>**HTTP / HTTPS**</summary>
<details>
<summary>HTTP 和 HTTPS 有什么区别？</summary>
HTTPS 可以理解为 HTTP + TLS。相比 HTTP 明文传输，TLS 提供加密、完整性保护和身份认证。TLS 握手阶段通过证书和非对称密码学完成身份认证与密钥协商，建立共享会话密钥，后续应用数据主要使用效率更高的对称加密传输。**不要把现代 TLS 固定说成“直接用服务器公钥加密并传输会话密钥”；更稳妥的是“通过非对称密码学完成认证和密钥协商”。**
</details>
</details>
<details>
<summary>**DNS**</summary>
<details>
<summary>DNS 是干什么的？域名解析的大致过程是什么？</summary>
DNS 用来把域名解析成 IP 地址。客户端通常先检查本地缓存，未命中后请求本地 DNS 解析器；本地 DNS 再依次查询根 DNS、顶级域 DNS 和权威 DNS，最终得到目标 IP 并返回。客户端到本地 DNS 常可理解为递归查询，而本地 DNS 向根、顶级域和权威 DNS 的过程通常是迭代查询。**递归 = 你帮我查到底；迭代 = 你告诉我下一站。不要把根服务器逐级指路说成递归。**
</details>
</details>
<details>
<summary>**URL 到页面显示**</summary>
<details>
<summary>浏览器输入 URL 到页面最终显示，大致发生了什么？</summary>
核心顺序：解析 URL → DNS 解析域名得到 IP → 建立 TCP 连接 → 如果是 HTTPS 再进行 TLS 握手 → 发送 HTTP 请求 → 服务端返回 HTTP 响应 → 浏览器解析 HTML / CSS / JavaScript 并渲染页面。**HTTPS 场景也必须先 DNS，再 TCP，再 TLS；不能在不知道目标 IP 时先进行 TLS。DNS 也不是“HTTP 协议自己的解析”。**
</details>
</details>
<details>
<summary>**TCP 可靠传输**</summary>
<details>
<summary>TCP 是怎么保证可靠传输的？</summary>
TCP 通过序列号给数据编号，接收方通过 ACK 确认已收到的数据；发送方在超时未收到 ACK 时进行超时重传，连续收到重复 ACK 时也可能触发快速重传。此外还通过校验和检测传输错误，并通过流量控制和拥塞控制调节发送速度。**只回答“ACK + 重传”不算错，但不够完整。核心记忆：序列号 + ACK + 重传 + 校验 + 流量控制 + 拥塞控制。**
</details>
</details>
<details>
<summary>**TCP 流量控制与拥塞控制**</summary>
<details>
<summary>TCP 的流量控制和拥塞控制有什么区别？</summary>
流量控制是为了**防止发送方发送过快导致接收方缓冲区来不及处理**，主要通过接收窗口 rwnd 实现；拥塞控制是为了**避免过多数据进入网络造成拥塞，发送方通过拥塞窗口 cwnd 调整发送速率**。实际可发送窗口通常同时受二者约束。**流量控制看 rwnd，拥塞控制看 cwnd；发送窗口通常受 min(rwnd, cwnd) 限制。**
</details>
<details>
<summary>TCP 拥塞控制有哪些经典机制？</summary>
经典八股通常记为慢启动、拥塞避免、快速重传、快速恢复。慢启动阶段 cwnd 从较小值开始并快速增长，达到 ssthresh 后进入拥塞避免，增长变得更平缓；连续收到重复 ACK 时可触发快速重传，并配合快速恢复调整窗口。**不是“快速失败重传”；标准术语是：慢启动、拥塞避免、快速重传、快速恢复。慢启动阶段 cwnd 通常近似指数增长，拥塞避免阶段更接近线性增长。**
</details>
</details>
## 操作系统
<details>
<summary>**进程与线程**</summary>
<details>
<summary>进程和线程有什么区别？</summary>
进程通常拥有独立的地址空间，是操作系统进行资源分配的基本单位；线程是 CPU 调度和执行的基本单位。同一进程中的线程共享堆、文件等进程资源，但各自拥有线程栈、程序计数器等线程私有状态。进程之间隔离性更强，而线程共享资源更多，通信方便但更容易出现并发问题。**标准表述：进程是资源分配的基本单位，线程是 CPU 调度和执行的基本单位。普通线程抛出未捕获异常通常只会结束该线程，并不一定导致整个进程崩溃。**
</details>
</details>
<details>
<summary>**进程间通信 IPC**</summary>
<details>
<summary>常见的进程间通信方式有哪些？</summary>
常见方式包括管道 Pipe、消息队列、共享内存、Socket 和信号。共享内存让多个进程直接访问同一块内存区域，速度通常较快，但需要额外同步；Socket 既可用于本机通信，也可用于跨机器通信。**除了管道和共享内存，还要记住：消息队列、Socket、信号。**
</details>
</details>
<details>
<summary>**死锁条件**</summary>
<details>
<summary>死锁产生需要满足哪四个条件？</summary>
死锁需要同时满足互斥、占有并等待、不可剥夺、循环等待四个条件；破坏其中任意一个，都可以从理论上避免死锁。**四个条件：互斥、占有并等待、不可剥夺、循环等待。记忆：互、占、不、环。**
</details>
<details>
<summary>lockInterruptibly() 是否等于“可剥夺锁”？</summary>
不是。lockInterruptibly() 允许正在等待锁的线程被 interrupt 后退出等待，但不会把已经被其他线程持有的锁强行抢走；持锁线程仍需主动 unlock。**interrupt 能让“等锁的人不等了”，但不能把“持锁人的锁抢走”，所以这不等于破坏不可剥夺条件。**
</details>
</details>
<details>
<summary>**虚拟内存与缺页**</summary>
<details>
<summary>什么是虚拟内存？为什么要使用虚拟内存？</summary>
虚拟内存为每个进程提供独立的虚拟地址空间，由操作系统和硬件把虚拟地址映射到物理内存。它可以实现地址抽象和进程隔离，让程序无需依赖具体物理地址；同时配合分页和按需加载，不必让所有数据始终驻留物理内存。**除了地址抽象和隔离，还要记住：分页 + 按需加载，让进程拥有更大的虚拟地址空间而不要求全部同时驻留物理内存。**
</details>
<details>
<summary>什么是缺页中断？</summary>
当程序访问某个虚拟页，而该页当前不在物理内存中时，CPU 会触发缺页异常进入内核。操作系统找到对应数据并装入物理页框，更新页表后，再重新执行原来的指令；如果访问的是非法地址，则可能直接使进程异常终止。**缺页不一定意味着“这个虚拟地址从未建立过映射”，核心是页表显示该页当前 not present；处理流程是调入页面 → 更新页表 → 重试指令。**
</details>
</details>
<details>
<summary>**用户态与内核态**</summary>
<details>
<summary>用户态和内核态有什么区别？什么时候会切换到内核态？</summary>
用户态权限受限，普通应用不能直接执行特权指令或随意访问硬件和内核空间；内核态权限更高，由操作系统内核执行资源管理和硬件相关操作。程序执行系统调用时会陷入内核态，此外异常和硬件中断也可能触发切换。**不只是系统调用；常见三类入口：系统调用、异常、中断。用户态与内核态的核心区别是权限级别不同。**
</details>
</details>
<details>
<summary>**I/O 模型与多路复用**</summary>
<details>
<summary>阻塞 I/O、非阻塞 I/O、I/O 多路复用和异步 I/O 有什么区别？</summary>
阻塞 I/O 调用 read 等操作时，如果数据未准备好，线程会阻塞等待；非阻塞 I/O 在数据未准备好时会立即返回，应用之后再重试；I/O 多路复用通过 select / poll / epoll 同时监听多个 fd，就绪后再处理；异步 I/O 则是提交请求后立即返回，由内核完成真正的 I/O 操作并在完成后通知应用。**不要把 Java NIO 直接等同于操作系统的 Non-blocking I/O；你说的“提交后立即返回，完成后由系统通知”更接近 AIO。多路复用的核心是一个线程 / 事件循环监听多个 fd。**
</details>
<details>
<summary>select、poll、epoll 有什么区别？</summary>
select 使用 fd_set 位图，通常受 FD_SETSIZE 限制，并且每次都需要传递和遍历整个 fd 集合；poll 使用 pollfd 数组，摆脱固定 1024 数量限制，但仍需要线性遍历所有 fd；epoll 通过 epoll_ctl 把 fd 注册到内核，通常用红黑树管理注册项、就绪链表保存活跃 fd，epoll_wait 直接返回已经就绪的 fd。**poll 不是“双向链表监听”，核心是 pollfd 数组；select 的“1024”和位图大小本质是同一个 FD_SETSIZE 限制；epoll 的优势不只是红黑树，而是注册一次 + 事件驱动 + 只返回就绪 fd。**
</details>
<details>
<summary>epoll 的 LT 和 ET 有什么区别？</summary>
LT（水平触发）下，只要 fd 仍处于可读 / 可写状态，就会继续通知；ET（边缘触发）更关注状态变化，通常只在从未就绪变为就绪时通知，因此收到事件后通常需要配合非阻塞 fd 循环读写直到 EAGAIN / EWOULDBLOCK。**LT：没处理完还提醒；ET：提醒一次后要尽量处理干净，通常读到 EAGAIN。**
</details>
</details>
<details>
<summary>**零拷贝**</summary>
<details>
<summary>什么是零拷贝？为什么能提高网络传输性能？</summary>
零拷贝是一类减少不必要数据复制和上下文切换的优化思想。传统 read + write 可能让数据在内核缓冲区、用户态缓冲区和 Socket 缓冲区之间多次复制；sendfile、mmap、splice 等技术可以减少用户态与内核态之间的额外复制，并配合 DMA 完成设备间的数据搬运。**零拷贝不等于“完全没有拷贝”，也不等于单纯“用 DMA 代替 CPU”；核心是减少不必要的 CPU 拷贝和用户态 / 内核态切换。**
</details>
</details>
<details>
<summary>**Copy On Write 与上下文切换**</summary>
<details>
<summary>什么是 Copy On Write？为什么 fork 要使用它？</summary>
fork 创建子进程时不会立即复制父进程全部物理内存，而是让父子进程各自的虚拟地址空间暂时映射到相同物理页；相关页通常先按只读方式共享，只有其中一方真正写入时才触发缺页异常，复制对应物理页并更新页表。这样可以减少 fork 的时间和内存开销。**不是“直接复用父进程的地址空间”；父子进程虚拟地址空间仍独立，只是暂时共享同一批物理页。记忆：fork 先共享，写时再复制。**
</details>
<details>
<summary>什么是上下文切换？需要保存和恢复什么？</summary>
上下文切换是 CPU 从一个线程或进程切换到另一个任务时，操作系统先保存当前执行现场，再加载另一个任务的现场。典型状态包括程序计数器 PC、CPU 寄存器、栈指针 SP 以及调度相关状态；进程切换还可能涉及地址空间 / 页表相关状态，因此通常比同进程线程切换更重。**核心记忆：保存现场 → 切换任务 → 恢复现场；至少要想到 PC、寄存器、SP。**
</details>
</details>

## AI应用开发
<details>
<summary>**RAG 基础与流程**</summary>
<details>
<summary>什么是 RAG？为什么需要 RAG？</summary>
RAG 是 Retrieval-Augmented Generation，即检索增强生成。它会先从外部知识库检索与问题相关的内容，再把检索结果作为上下文交给大模型生成答案，用于补充时效性知识、私有知识并降低幻觉。**标准中文是“检索增强生成”；RAG 只能降低幻觉，不能保证完全消除幻觉。**
</details>
<details>
<summary>RAG 的完整流程是什么？</summary>
离线构建：文档加载 / 清洗 → Chunk 切分 → Embedding → 写入向量库 / 建索引；在线查询：用户问题 → Query Embedding → 召回 → 可选 Rerank → 拼接上下文 → LLM 生成。查询改写、多路召回、Hybrid Search 等属于常见优化手段。
</details>
</details>
<details>
<summary>**Embedding 与 Chunk**</summary>
<details>
<summary>Embedding 是什么？为什么要把文本转成向量？</summary>
Embedding 会把文本映射为高维向量，使语义相近的文本在向量空间中更接近，从而可以用余弦相似度、点积等方式进行语义检索。**不要说“文本之间无法建立语义关联”；更准确是原始文本不方便直接用统一的数值方式计算语义相似度。**
</details>
<details>
<summary>Chunk 为什么不能切得太大或太小？</summary>
Chunk 太大会混入更多无关信息、增加噪声并消耗更多上下文；太小则容易破坏语义完整性。通常还会设置一定 overlap，避免关键信息刚好被切断。**核心记忆：太大噪声多，太小语义碎，Overlap 防边界切断。**
</details>
</details>
<details>
<summary>**召回、Rerank 与混合检索**</summary>
<details>
<summary>召回和 Rerank 有什么区别？</summary>
召回负责从大规模知识库中快速找出一批候选，可使用向量检索、BM25 或混合检索；Rerank 再用更精细的相关性模型对 query + candidate 重新打分排序。**Rerank 的核心是重新打分精排，不等于去重或截断；去重和 Top-K 截断通常属于后处理。**
</details>
<details>
<summary>什么是 Hybrid Search？</summary>
Hybrid Search 即混合检索，常见做法是结合向量检索和 BM25。向量检索擅长语义匹配，BM25 更擅长错误码、编号、专有名词等字面精确匹配。记忆：Vector 找意思，BM25 找字面。
</details>
<details>
<summary>为什么向量召回后通常还需要 Rerank？</summary>
向量相似度高不代表该 Chunk 一定最适合回答当前问题，因此常先快速召回一批候选，再使用 Rerank 精排，最后截取最相关的 Top-K 进入上下文。记忆：Recall 求广，Rerank 求准。
</details>
</details>
<details>
<summary>**RAG 与 Fine-tuning**</summary>
<details>
<summary>RAG 和 Fine-tuning 有什么区别？</summary>
RAG 在推理时加入外部知识，不修改模型参数，适合频繁变化、需要实时更新或私有的知识；Fine-tuning 会继续训练并修改模型参数，更适合调整模型行为、输出风格、格式和特定任务能力。**不要把微调主要理解成“把稳定知识灌进模型”；Fine-tuning 更偏行为和能力适配，RAG 更适合知识更新。**
</details>
</details>
<details>
<summary>**Prompt Injection、Tool Calling、Agent**</summary>
<details>
<summary>什么是 Prompt Injection？为什么 Tool Calling 场景更危险？</summary>
Prompt Injection 是攻击者通过恶意提示词诱导模型忽略原有指令或业务约束。它既可能来自用户输入，也可能来自网页、文档等外部内容。带 Tool Calling 时风险更高，因为模型可能进一步触发邮件、数据库、文件系统等真实操作，因此需要最小权限、参数校验以及高风险操作确认。**除了直接用户输入，还要记住间接 Prompt Injection；Tool Calling 场景的风险在于“做错事”，不只是“说错话”。**
</details>
<details>
<summary>什么是 Function Calling / Tool Calling？</summary>
应用会把工具名称、描述和参数 Schema 提供给模型，模型根据语境选择工具并生成结构化参数；真正执行通常由应用 Runtime 完成，再把结果返回模型继续生成。在 Java 框架中可以通过工具注册表、注解扫描和反射等方式完成发现与调用。**反射是 Java 中常见的实现手段，但不是 Tool Calling 协议本身的必需机制；模型主要负责“选工具 + 填参数”，程序负责真正执行。**
</details>
<details>
<summary>Agent 和单次 Tool Calling 有什么区别？</summary>
单次 Tool Calling 通常完成一次工具选择和执行；Agent 会根据当前状态和工具结果形成多步循环，不断重新判断下一步动作，直到完成目标或触发停止条件。记忆：Tool Calling 是一次动作，Agent 是多步闭环。
</details>
</details>
<details>
<summary>**采样参数**</summary>
<details>
<summary>Temperature、Top-p、Top-k 分别是什么？</summary>
Temperature 用来调整概率分布的尖锐程度，越低越稳定，越高随机性越强；Top-p 按概率从高到低保留累计概率达到 p 的最小候选集合；Top-k 只保留概率最高的前 k 个 Token。**Temperature 不是“随机取样范围”；temperature=1 也不是“随便乱选”，而是更接近按原始概率分布采样。也不要说“Top0”。**
</details>
</details>
<details>
<summary>**Token 与上下文窗口**</summary>
<details>
<summary>Token 是什么？上下文窗口是什么？</summary>
Token 是模型处理和生成文本的基本单位，具体如何切分由 Tokenizer 决定，并不固定等于一个单词或一个汉字。上下文窗口是一次推理能处理的 Token 总量上限，通常会包含系统提示词、历史消息、用户输入、RAG 内容、Tool 返回结果以及输出。**Token 不是“大模型思考的最小单位”，更准确是模型处理和生成文本的基本单位。**
</details>
</details>
<details>
<summary>**幻觉与 RAG 优化排查**</summary>
<details>
<summary>大模型为什么会产生幻觉？</summary>
大模型本质上根据上下文预测后续 Token，它的目标是生成统计上合理的文本，并不天然保证事实正确。训练数据错误、冲突或过时，模型缺少相关知识、上下文不足，以及 RAG 召回错误等都可能导致幻觉。**核心不是“模型记不住所有东西”，而是 LLM 本质上做概率生成，语言上合理不等于事实一定正确。**
</details>
<details>
<summary>RAG 召回效果差，可以从哪些方向优化？</summary>
可以从文档清洗与 Chunk、Embedding 模型、Query Rewrite、Top-K、Metadata Filter、Hybrid Search、Rerank 等方向优化，并通过固定测试集持续评估召回率和相关性。**除了增加召回方式和调 Rerank，还要记住 Chunk、Embedding、Top-K 和评测集。**
</details>
<details>
<summary>RAG 出现幻觉，怎么判断是检索问题还是生成问题？</summary>
先检查实际召回内容是否包含回答问题所需的正确信息；如果召回结果不相关或缺关键事实，主要是检索问题；如果上下文已经正确完整但模型仍编造或误解，则更偏生成问题。记忆：先看拿到的资料对不对，再看模型有没有按资料回答。
</details>
</details>
<details>
<summary>**流式输出**</summary>
<details>
<summary>什么是流式输出？为什么 LLM 接口常用流式输出？</summary>
流式输出是模型生成过程中持续把增量结果发送给客户端，而不是等待完整答案后一次性返回，可以明显降低首字延迟、改善长回答体验。SSE 是常见实现方式之一，也可以使用其他流式 HTTP 或 WebSocket。**流式输出不等于 SSE；Streaming 是返回模式，SSE 只是常见实现方式。**
</details>
</details>
<details>
<summary>**MCP**</summary>
<details>
<summary>什么是 MCP？它和 Tool Calling 有什么关系？</summary>
MCP 是一种标准协议，用来统一 AI 应用与外部工具、数据源和提示资源之间的连接方式。MCP Server 可以暴露 Tools、Resources、Prompts，Host / Client 负责发现和调用这些能力。Tool Calling 解决“模型怎么选择并调用工具”，MCP 更偏向解决“外部能力如何被标准化暴露、发现和复用”。**MCP 不只是“存很多 Tool Calling 函数的进程”，Server 还可以提供 Resources 和 Prompts；而且它不要求一定是独立进程。**
</details>
</details>
<details>
<summary>**向量数据库与 ANN**</summary>
<details>
<summary>向量数据库是干什么的？和关系型数据库有什么区别？</summary>
向量数据库主要存储 Embedding 及其关联文本 / metadata，并针对相似度检索进行优化，常用于从大量向量中快速找到最相似的 Top-K。传统关系型数据库更擅长结构化数据的精确查询、范围查询、Join 和事务。**向量数据库的核心价值不只是“能存向量”，而是高效做相似度检索。**
</details>
<details>
<summary>为什么不直接和所有向量逐个算相似度？</summary>
全量暴力计算在数据规模大时成本很高，因此通常使用 ANN（Approximate Nearest Neighbor，近似最近邻）索引，通过牺牲少量精确性换取更高检索速度。常见索引包括 HNSW、IVF。
</details>
<details>
<summary>HNSW 和 IVF 大致怎么加速检索？</summary>
HNSW 使用分层近邻图，上层用于快速粗定位，再逐层向下精搜；IVF 则先把向量聚类分桶，查询时只搜索最相关的几个簇，而不是扫描全部向量。**HNSW 更准确说是“分层近邻图”，不是重点记“多层有向图”；记忆：HNSW = 图导航，IVF = 聚类分桶。**
</details>
</details>
<details>
<summary>**Top-K 与 Query Rewrite**</summary>
<details>
<summary>RAG 中的 Top-K 是什么？K 太大或太小有什么问题？</summary>
Top-K 表示检索阶段保留的候选数量。K 太小可能漏掉关键文档、降低召回率；K 太大则会引入更多噪声，同时增加 Rerank 和上下文 Token 成本。**K 小怕漏，K 大怕噪声和成本。**
</details>
<details>
<summary>什么是 Query Rewrite？为什么需要查询改写？</summary>
Query Rewrite 是在检索前把用户原始问题改写成更适合检索的形式，例如补全上下文、消除歧义、加入关键术语或拆分复杂问题，从而提高召回效果。**Query Rewrite 的首要目标是优化检索，不只是让最终回答更好；最大风险是语义漂移，改写后偏离用户原意。**
</details>
</details>
<details>
<summary>**RAG 评估**</summary>
<details>
<summary>怎么评估一个 RAG 系统效果好不好？</summary>
检索侧可以看 Recall@K，判断正确文档有没有进入候选；也可以看 Reciprocal Rank / MRR，衡量正确结果是否排得足够靠前。多路召回场景下，还可以分别观察各路召回、融合排序以及 Rerank 前后的目标文档排名变化。业务上也可以增加关键词、实体或规则命中率等自定义指标。生成侧则需要继续评估答案正确性、相关性，以及是否忠于召回上下文。**不能只看“正确内容有没有被召回”，还要看它排得靠不靠前；如果评估整个 RAG，还要补生成侧的正确性和 Faithfulness。**
</details>
</details>
